OMNIVLA × JETSON AGX ORIN × ROS 1

omnivla_real の構成

学習 PC でコース走行の rosbag から OmniVLA を学習し、Jetson ではサブゴール画像を切り替えながら走る。 Jetson の中は 推論コンテナ と ROS 1 コンテナ の 2 つに分かれている。

実行手順は README にあります。

全体

学習 PC GPU (PyTorch) ROS 1 ロボット データ

走行中の 1 ステップ

③ で最後のサブゴールに着いたら停止。① 〜 ⑧ は新しいカメラ画像が来るたびに繰り返す (上限はカメラの周期と推論時間)。過去画像は学習データと同じ 3Hz ごとに積む。⑧ の指示値は 10Hz で出し続ける。

なぜ 2 つのコンテナに分けるか

  • ROS 1 Noetic は Ubuntu 20.04 用。Jetson で GPU が使える PyTorch は JetPack ごとに Ubuntu が決まる (JetPack 6 は 22.04, 5 は 20.04)。
  • 分けておけば、JetPack が決まっていなくても ROS 1 側はそのまま。推論コンテナのベースイメージだけを JetPack に合わせて選べばよい。
  • ROS 1 コンテナは PyTorch 無し (C++ のノード. 起動時の設定の読み込みにだけ python3 を使う) なので、既存の ROS 1 環境にも入れやすい。

コンテナ間の通信

やりとりは「画像を渡して、その結果を待つ」だけなので、リクエスト / レスポンス型で、追加のライブラリが要らないものを選んだ。

方式形追加で必要なもの判断
HTTPリクエスト / レスポンスなし (Python は標準ライブラリ、C++ は同梱のヘッダ)採用。curl :8765/info で生存確認できる
ZeroMQリクエスト / レスポンス両コンテナに pyzmq同じくらい妥当。少し軽い
MQTT配信 / 購読ブローカー (mosquitto など)結果を待つ使い方に合わない。プロセスが 1 つ増える
gRPCリクエスト / レスポンスgrpcio · protobuf7B の依存 (protobuf<5) とぶつかりやすい
  • 同じ Jetson の中 (localhost) だけの通信。ロボットの他のノードとのやりとりは今まで通り ROS 1 のトピック。
  • カメラの JPEG はデコードせずに送り、切り抜き・縮小は推論コンテナが学習時と同じ関数で行う。Python 版のノードと同じ結果になる (CI で確認)。
  • 推論コンテナは送られた画像を覚えている。観測履歴とサブゴール画像は 2 回目から名前だけを送るので、1 回に送るのは新しい画像 1 枚。
  • 通信部分は omnivla_real/remote.py (推論コンテナ) と policy_client.cpp (ROS 1 コンテナ) だけに閉じているので、他の方式に替えても残りは変わらない。
Jetson ではまだ測っていない。開発環境で偽のモデルを使ったときは、通信と前処理を含めて 1 回 約 6 ms だった。

デバッグ画面

ROS 1 コンテナ (C++ のノード) が小さな Web サーバを持っていて、ロボットと同じネットワークのブラウザから http://<Jetson の IP>:8080 で開ける。

表示中身
いまの画像モデルに入れた画像 (切り抜き・縮小の後) に、予測した 8 点の軌跡を重ねたもの
サブゴールいま目指している画像と、そこまでの距離。下にコースのサブゴールが並ぶ
指示値ロボットに出している v と ω、直近 60 秒の履歴
予測した軌跡上から見た図 (0.5 m 方眼)
サブゴールの判定画像の類似度と切り替えのしきい値、推論時間と回数
  • 停止ボタンか Esc キーで止まる。画面を開いている人がいないときは、画面用の画像を作らない。
  • 画像に重ねる軌跡は robot.yaml の camera (画角・高さ・下向きの傾き) で計算する。実機に合わせると重なりが正しくなる。
