なぜ 2 つのコンテナに分けるか

  • ROS 1 Noetic は Ubuntu 20.04 用。Jetson で GPU が使える PyTorch は JetPack ごとに Ubuntu が決まる (JetPack 6 は 22.04, 5 は 20.04)。
  • 分けておけば、JetPack が決まっていなくても ROS 1 側はそのまま。推論コンテナのベースイメージだけを JetPack に合わせて選べばよい。
  • ROS 1 コンテナは PyTorch 無し (rospy · numpy · Pillow · PyYAML だけ) なので、既存の ROS 1 環境にも入れやすい。

コンテナ間の通信

やりとりは「画像を渡して、その結果を待つ」だけなので、リクエスト / レスポンス型で、追加のライブラリが要らないものを選んだ。

方式形追加で必要なもの判断
HTTPリクエスト / レスポンスなし (Python 標準ライブラリ)採用。curl :8765/info で生存確認できる
ZeroMQリクエスト / レスポンス両コンテナに pyzmq同じくらい妥当。少し軽い
MQTT配信 / 購読ブローカー (mosquitto など)結果を待つ使い方に合わない。プロセスが 1 つ増える
gRPCリクエスト / レスポンスgrpcio · protobuf7B の依存 (protobuf<5) とぶつかりやすい
  • 同じ Jetson の中 (localhost) だけの通信。ロボットの他のノードとのやりとりは今まで通り ROS 1 のトピック。
  • 画像は無圧縮で送るので、ノードの中で推論した場合と同じ結果になる (CI で確認)。
  • 通信部分は omnivla_real/remote.py だけに閉じているので、他の方式に替えても残りは変わらない。
通信にかかる時間は Jetson ではまだ測っていない。画像 7 枚 (約 1.6MB) で数 ms の見込みで、7B の推論 (数百 ms 以上) に比べれば小さい。
